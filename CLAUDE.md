# CLAUDE.md

Bootstrap-контекст для проєкту Manifay (тестове завдання, full-stack: Nuxt 4 + Laravel).

## ТЗ (оригінал)

### Full-stack Test Assignment
Frontend-focused with Backend fundamentals

### 1. Загальна інформація

Мета тестового завдання — оцінка перед технічною співбесідою:
- frontend-навичок (Nuxt / Vue / UX / forms)
- базових backend-навичок (API, data modeling, validation)
- інженерного мислення
- вміння працювати з реальним стеком
- здатності пояснювати власні рішення

Рекомендований час: 4-6 годин (допускається часткова реалізація з поясненнями).

### 2. Контекст проєкту

Система, яка автоматизує роботу бухгалтерів: створення та облік рахунків (invoices), редагування фінансових даних, перегляд списку документів, контроль коректності сум і дат.

Задача — реалізувати мінімальний, але реалістичний full-stack модуль для роботи з інвойсами.

### 3. Технічний стек

**Frontend:** Nuxt 4, Vue 3.5, TailwindCSS 4
**Backend:** PHP 8.2+, Laravel або Symfony
**Data:** MySQL або PostgreSQL
**Environment:** Docker (docker-compose)

### 4. Функціональні вимоги — BACKEND PART

#### 4.1 Модель Invoice

Мінімум полів:
- `id` (uuid або auto increment)
- `number` (string, унікальний)
- `supplier_name` (string)
- `supplier_tax_id` (string)
- `net_amount` (decimal)
- `vat_amount` (decimal)
- `gross_amount` (decimal)
- `currency` (string, наприклад UAH)
- `status` (pending | approved | rejected)
- `issue_date` (date)
- `due_date` (date)
- `created_at`, `updated_at`

#### 4.2 API Endpoints

1. `GET /api/invoices` — список, базове сортування (`created_at desc`), pagination опціонально
2. `GET /api/invoices/{id}` — один інвойс
3. `POST /api/invoices` — створення. Валідація мінімум:
   - `number` — обов'язкове, унікальне
   - `net_amount > 0`
   - `vat_amount >= 0`
   - `gross_amount = net_amount + vat_amount`
   - `due_date >= issue_date`
4. `PUT /api/invoices/{id}` — оновлення. Дозволене тільки для статусу `pending`, перевалідація сум і дат.

#### 4.3 Backend вимоги

REST API, JSON responses, HTTP status codes, server-side validation, чиста структура (controllers / services / validation). **Аутентифікація не потрібна.**

### FRONTEND PART

**5.2 Деталі інвойсу `/invoices/[id]`**

Увага на: розділення frontend/backend відповідальностей, коректну бізнес-логіку, зрозумілий код, роботу з edge cases.

## Архітектурні рішення (зафіксовані в чаті перед стартом коду)

1. **Немає create-форми на фронтенді.** Frontend-секція ТЗ (п.5-6) описує тільки список/деталі/редагування — форми створення там немає, хоча `POST /api/invoices` вимагається бекендом (п.4.2). Рішення: реалізувати `POST` повністю на бекенді (з валідацією), а демо-дані наповнювати через `DatabaseSeeder`. Задокументувати в README як свідомий вибір, не пропущену вимогу.

2. **Немає механізму зміни статусу.** ТЗ ніде не описує, як інвойс переходить `pending → approved/rejected` (жодного endpoint'у чи UI). Рішення: не додавати окремий API — `DatabaseSeeder` одразу створює частину інвойсів зі статусами `approved`/`rejected`, щоб на реальних даних можна було продемонструвати заблоковану edit-форму.

3. **`gross_amount` завжди рахує бекенд**, ігноруючи будь-яке клієнтське значення в payload (навіть якщо воно прийде) — не довіряти клієнтській арифметиці для фінансових даних. Фронтенд показує live-перерахунок лише як UX-прев'ю.
   **Свідома реінтерпретація ТЗ:** п.4.2 буквально формулює це як правило валідації ("gross_amount = net_amount + vat_amount"), тобто ніби клієнт надсилає `gross_amount`, а бекенд перевіряє рівність. Замість цього `gross_amount` взагалі не приймається як вхідне поле — інваріант виконується тим, що бекенд сам його обчислює. Строгіше й безпечніше за буквальне трактування (немає способу надіслати неузгоджене значення), той самий інваріант виконано. Пункт для README п.8.2.

4. **Крос-польова валідація `due_date >= issue_date`.** У формі редагування (п.6) `issue_date` не є редагованим полем — тільки `net_amount`, `vat_amount`, `due_date`. Тому zod-схема звіряє `due_date` з зафіксованим `issue_date`, отриманим разом з інвойсом при завантаженні форми, а не з полів самої форми.

5. **Точність грошових обчислень на фронтенді.** Live-перерахунок `gross_amount = net_amount + vat_amount` округлюється до 2 знаків (уникнення float-похибок на кшталт 0.1+0.2 у JS).

6. **CORS** — увімкнено напряму на бекенді (`config/cors.php`, `allowed_origins` = `FRONTEND_URL` з `.env`), без Nuxt server-проксі. Простіше для двоконтейнерного docker-compose (backend:8000 + frontend:3000), не додає зайвого проміжного шару заради задачі, де його немає що ховати.

## Статичний аналіз (простіше, ніж у попередньому проєкті)

Без GrumPHP-оркестрації, без Deptrac (немає Ports/шарів — нічим перевіряти межі). Git hooks — прості трековані shell-скрипти в `.githooks/` (не Husky — зайва npm-залежність заради того, що вміє сам git), без окремого фреймворка-оркестратора.

- **Backend:** `composer lint` (Laravel Pint, форматування) + `composer analyse` (Larastan/PHPStan рівень 5).
- **Frontend:** `npm run lint` (`@nuxt/eslint`, офіційний zero-config модуль) + `npm run typecheck` (`nuxt typecheck` через vue-tsc).
- **Git hooks:** `pre-commit` — Pint + ESLint (швидко, кожен коміт); `pre-push` — Larastan + typecheck (повільніше, рідше). Через `docker compose exec`, тому вимагає запущеного `docker compose up`. `core.hooksPath` — локальне налаштування (`git config core.hooksPath .githooks`), не переноситься автоматично при клонуванні — задокументовано в README.

**Знахідки під час першого прогону (не косметика, реальні речі):**
- Larastan не резолвив типи з Laravel 12-івського `casts(): array`-методу (каскадом ламало аналіз `UseCase`/`FormRequest`) — повернув класичний `protected $casts = [...]`, поведінково ідентично.
- `InvoiceResource`'у бракувало `@mixin Invoice` — без нього Larastan не знає, які magic-властивості (`$this->id` тощо) валідні.
- `zod` встановився в 4.x (не запінили версію при `npm install`), хоча `@vee-validate/zod` вимагає `^3.24` — невідповідність із власною ж таблицею версій у CLAUDE.md. Запінено `^3.24`.
- `typescript` резолвнувся в experimental `^7.0` (несумісно з `typescript-eslint`) — запінено `^5.7`.
- zod-схема типізувала `due_date` як `Date` (`z.coerce.date()`), а HTML `<input type="date">` і API працюють зі string — typecheck зловив розходження типів. Порівняння дат лишилось у `.refine()`, тип поля став `string`.

## Архітектура бекенду

**Схема:** `Controller (тонкий)` → `UseCase` → `Repository` (Eloquent). **Без Ports/інтерфейсів, без окремого Domain-шару.**

- **Controller** — лише HTTP: приймає `FormRequest` (валідація), викликає `UseCase`, повертає `Resource`/HTTP-код. Жодної бізнес-логіки.
- **UseCase** — одна публічна дія на клас (наприклад `CreateInvoiceUseCase`, `UpdateInvoiceUseCase`). Тут живе бізнес-логіка, яка не належить ні контролеру, ні моделі: `gross_amount` рахує сервер сам (не довіряє клієнтському значенню з payload), `update` дозволений лише для `status == pending`.
- **Repository** — конкретний Eloquent-клас (не інтерфейс), інкапсулює запити. `UseCase` типізує його напряму в конструкторі — Laravel-контейнер резолвить автоматично (autowiring), жодних явних біндингів у `ServiceProvider` не потрібно, окремий "ServiceContainer" писати не треба — вбудований контейнер Laravel і так це робить безкоштовно.
- **Model = domain-об'єкт** — окремого Domain-шару немає, Eloquent-модель одночасно і persistence, і носій даних. Дисципліна: уся бізнес-логіка виключно в `UseCase`, модель не містить нічого, крім `$fillable`/`$casts`/зв'язків.

**Свідомо відкинуто (Ports/інтерфейси):**
- Плюси підходу: пряме співпадіння з ТЗ п.4.3/п.7 ("чиста структура", "розділення відповідальностей"), один явний дім для бізнес-правил, менше боілерплейту під бюджет 4-6 год, простіше читати рев'юеру.
- Мінуси, свідомо прийняті: `UseCase` жорстко зв'язаний з конкретним Eloquent-репозиторієм (заміна сховища неможлива без правки UseCase — не проблема тут, один бекенд); юніт-тест `UseCase` в ізоляції без реальної БД складніший без інтерфейсу (mock конкретного класу через Mockery замість мокання інтерфейсу); ризик просочування бізнес-логіки в модель без інтерфейсного бар'єру — мітигується дисципліною, не структурою.
- Це прямий кандидат у відповідь README п.8.3 ("що покращив би в production") — додав би Ports/інтерфейси, якби знадобилась заміна сховища чи чисте юніт-тестування без БД.

## Архітектура фронтенду

**Структура папок — мінімалістична конвенція Nuxt 4** (без власного feature-folder групування):

```
app/
  pages/
    index.vue             # редірект на /invoices
    invoices/
      index.vue           # список
      [id].vue            # деталі + вбудована edit-форма
  components/
    InvoiceStatusBadge.vue
    InvoiceEditForm.vue
  composables/
    useInvoices.ts        # useFetch список
    useInvoice.ts         # useFetch один інвойс + update
  schemas/
    invoice.schema.ts     # zod-схема для edit-форми
  types/
    invoice.ts            # TS-тип Invoice
  utils/
    formatDate.ts         # форматування дат для read-only відображення
  app.vue
nuxt.config.ts
```

Nuxt 4 змінив дефолтну структуру — `pages/`/`components/`/`composables/`/`layouts/` очікуються всередині `app/`, `server/` лишається окремо на корені. Йдемо за цією конвенцією без додаткових вигадок: auto-import, жодного явного `import` компонентів/composables у `pages/`.

**Свідомо відкинуто:** feature-folder групування (`features/invoices/*`) — довелось би розширювати `nuxt.config.ts` (`components.dirs`, `imports.dirs`), щоб auto-import бачив нестандартні директорії. Виправдано лише при кількох фічах; тут фіча одна.

**Обов'язково зафіксувати в README (п.8.1 "Як ти структурував frontend і backend?"):** плоска Nuxt-конвенція — це свідомий вибір під формулювання ТЗ п.2 "реалізувати **мінімальний, але реалістичний** full-stack модуль" — мінімалізм структури тут відповідає вимозі напряму, а не є недоглядом. Пояснити паралель із рішенням по бекенду (UseCase без Ports з тієї ж причини).

## UX edge cases (каталог для README, п.8 питання 4)

**Список:**
- порожній список — окремий стан, не порожня таблиця
- помилка завантаження (500/мережа) — retry, не вічний спінер
- повільна мережа — loading-скелетон з невеликою затримкою показу
- довгі значення в колонках — truncate + tooltip
- некоректні/null дані з бекенду — graceful fallback, не крах UI

**Деталі:**
- невалідний/неіснуючий `id` в URL — 404, не вічний спінер
- race condition (інвойс змінили/видалили між списком і деталями)
- форматування дуже великих сум

**Форма редагування:**
- заблокована форма для `status != pending` — з поясненням чому, не просто disabled
- гонка статусу між завантаженням форми і сабмітом (422/409 обробка)
- подвійний сабміт (disable кнопки на час запиту)
- локаль десяткового роздільника (кома замість крапки — важливо для UA-бухгалтерів)
- округлення при live-перерахунку `gross_amount`
- межові значення (`net_amount = 0` invalid, дуже великі числа, від'ємні)
- втрата мережі під час сабміту — не скидати введені дані
- незбережені зміни при виході зі сторінки (опційно)

**Системні:**
- бекенд недоступний повністю — явний error state, не тиша
- CORS/проксі не налаштовано — запити мовчки не працюють

## Правила комітів

**Conventional Commits** (`type(scope): опис`) — перенесено з попереднього проєкту для узгодженості стилю.

Формат: `type(scope): опис`
- `type` — один з: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `style`, `perf`
- `scope` — шар або сутність: `invoices`, `frontend`, `backend`, `docker`, `cors`, `readme` тощо
- `опис` — imperative, малими літерами, без крапки в кінці, макс. 72 символи

Приклади:
```
feat(invoices): CreateInvoiceUseCase + gross_amount server-side calc
fix(cors): allowed_origins з FRONTEND_URL замість хардкоду
refactor(backend): UseCase без Ports — тонкий контролер
docs(readme): відповіді на 4 питання ТЗ
```

**Формат повідомлення НЕ enforced автоматично** (`.githooks/pre-commit` перевіряє лише код — Pint+ESLint, — не текст коміту; дотримуємось формату вручну). Якщо додати перевірку — той самий regex, що й у попередньому проєкті: `/^(feat|fix|refactor|docs|test|chore|style|perf)\(.+\): .{1,72}$/`.
